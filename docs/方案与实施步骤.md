# 外星仔加速器 · 模拟器端自动签到

> 在 MuMu 模拟器里跑一个 UI 自动化脚本，每天自动把「看广告领时长」的三档额度刷满。
> 本文写原理与踩坑；入口和快速开始见根目录 `README.md`。

---

## 一、核心原理

**发奖判定不在广告页上，在宿主 App 里。**

只要广告 Activity 存活够时间，把宿主主界面拉回前台就自动发奖：

```
点「看广告 领时长」 → 等广告 Activity 起来 → 原地停 15 秒 → 拉回主界面 → 校验时长
```

不需要点任何按钮，不需要识别广告内容，也不需要关落地页。15 秒足够
（脚本给 15 s + 0~4 s 随机抖动）。

### 为什么不挑广告联盟

实测遇到三个联盟，UI 完全不一样，同一套逻辑全部通过：

| 联盟 | Activity | 领奖按钮文案 |
|---|---|---|
| 快手 KSAdSDK | `WMPortraitActivity` | 我要直接拿奖励 |
| 倍孜 BeiZi | `BeiZiNewRewardVideoActivity` | 观看21秒广告领取奖励 |
| 穿山甲 bytedance | `PortraitTransparentAdActivity` | （全屏视频，无按钮） |

因为压根不需要看广告长什么样，「不同广告不一样」这个问题自然消失。

### 反证

不等够时间直接穿透跳过 → 主界面显示「广告加载失败，点击重试」，进度不变。
时间没到就是不发。

---

## 二、为什么不是「调接口」

| 路线 | 结论 |
|---|---|
| 抓包 + 复现协议 | 已封死。曾有人做过（GitHub `etalien-auto`），官方连续加固：8 秒间隔风控 → 24h 补发限额 → 砍掉补发接口 → 换 token 认证，项目已公告失效 |
| Hook 客户端回调 | 无效。发奖由服务端按广告播放记录校验，客户端伪造过不了 |
| UI 自动化 + 停留计时 | 采用。走的是「真人看广告」的正常链路，协议层无从封堵 |

**一个反直觉的实测结果**：存在「UI 提示领取失败、但时长确实增加」的情况。
所以校验一律以后端数据为准（时长增量），不信任何 UI 提示。

## 三、额度体系

| 档位 | 次数（实测） | 单次收益 | 满额后文案 |
|---|---|---|---|
| 阶段一 | 9 次 | 20 分钟 | 已完成 |
| 阶段二 | 3 次 | 30 分钟 | 已完成 |
| 加油包 | ≥7 次 | 10 分钟 | 已完成 |

单日满额 ≈ 19 轮 ≈ 4 小时可暂停时长，耗时约 20 分钟（含每轮 6~14 秒随机间隔）。

### 实测时间线

```
起步                     2 时 0 分
├ 阶段一 9 次 × 20 分    → 3 时 0 分
├ 阶段二 3 次 × 30 分    → 4 时 30 分
└ 加油包 7 次 × 10 分    → 6 时 0 分
```

三档全满后主按钮变成「今日广告已看完，请明日再来」，脚本检测到就收工。
脚本按「时长是否增加」推进，不依赖具体文案。

## 四、环境依赖

| 项 | 值 |
|---|---|
| 模拟器 | MuMu 12，装非系统盘；给 4 GB 内存、4 核 |
| adb | 模拟器自带，路径填进 `config.json` 的 `adb_path` |
| 设备 | MuMu 新版 `127.0.0.1:16384`，老版 `127.0.0.1:7555` |
| Python | 3.8+，依赖见根目录 `requirements.txt` |

凡是因机器而异的值（模拟器路径、adb 路径、OAID、设备端口）都不写死在代码里，
统一放 `config.json`（已被 `.gitignore` 忽略）。

### OAID 这一关

MuMu 默认伪装成 Xiaomi，但它没有 MIUI 的 OAID 服务 → 广告 SDK 报
`oaid sdk not find` → 广告平台回 `无广告填充 code=1010` → 广告永远加载不出来。

脚本里的 `ensure_ready()` 每次自动做这件事（幂等）：

```bash
setprop persist.oaid <config.json 里填的 UUID>
/data/adb/ksud resetprop ro.product.manufacturer OnePlus   # 其余 7 个 ro.product.* 同理
```

品牌改成 OnePlus（OPPO 系）后，广告 SDK 会走 OPPO 路径去读 `persist.oaid`。

`ro.*` 是运行时覆盖，**MuMu 每次重启都会还原**，所以每次运行前都要重刷；
`persist.oaid` 是持久属性，重启保留。

## 五、开机自动执行

每次登录 Windows 触发一次，同一天只跑一次。完整流程：

```
登录 Windows
  └ 等 2 分钟（让开机先稳定）
  └ 今天跑过没？→ 跑过就退出
  └ MuMuManager 拉起模拟器（约 11 秒）
  └ 等 adb 就绪 → 注入 OAID + 品牌属性
  └ 拉起外星仔 → 循环刷满三档额度（约 20 分钟）
  └ 记录日期 → 关闭模拟器
```

### 触发方式：注册表 Run 键

```
HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run\EtalienDailyCheckin
  = "<python 目录>\pythonw.exe" "<项目目录>\scripts\checkin.py" --delay 120
```

`pythonw.exe` 无窗口、不弹黑框；`--delay 120` 是登录后再等 2 分钟，避开开机高峰。

```bash
$PY scripts/checkin.py --install     # 写入 Run 键
$PY scripts/checkin.py --uninstall   # 移除
```

**为什么不用任务计划程序**：部分环境的安全策略把 `schtasks.exe` 列入了程序黑名单，
PowerShell 与 COM 注册同样被拦（实测 `E_ACCESSDENIED`）。Run 键是等效且零权限的实现，
同样在登录时触发。

**为什么不用启动文件夹的 `.cmd`**：那条路要多经过一层 shell，而且写文件时路径容易
变成正斜杠，`start` 不认。Run 键直接调 `pythonw.exe`，链路最短，任务管理器
「启动」标签里也能看到、能禁用。

### 每日去重

状态在 `output/state.json`，字段含义与判定规则见 `README.md`。这里只记两个容易踩的点：

- `save_state()` 是 merge 语义。**跨天时若发现 `date` 变了，必须立即丢弃全部旧字段**，
  否则昨天的 `all_done=true` 会漏进今天，当天的额度被直接吞掉（开发时实测踩到过）。
- 凌晨 0-6 点看到「已看完」多半是前一天的额度没刷新，这个时间段不认它。

```bash
$PY scripts/checkin.py --state       # 看当前状态（不连模拟器）
```

## 六、踩坑速查

| 坑 | 处理 |
|---|---|
| `oaid sdk not find` / `无广告填充 1010` | 见第四节，刷品牌属性 + `persist.oaid` |
| `adb root` 后 ksud 报 Permission denied | `adb root` 会重启 adbd，重启期间仍是 shell(uid=2000)。改用 `MuMuManager.exe sh` 通道，身份直接是 uid=0 |
| 冷启动后品牌属性刷不进去 | 同上。`is_android_started` 早于系统就绪，靠 `mumu_sh` + 重试兜住 |
| MuMu 重启后变横屏（1920x1080） | `MuMuManager.exe setting -v 0 -k resolution_mode -val phone.1` 固定竖屏 |
| 主按钮 `UIADSubmitText` 找不到 | 竖屏分辨率下页面过长、按钮被挤出滚动区，`ensure_on_ads_page()` 会上滑 4 次兜底 |
| 满额后进度读不到 | 文案从 `N / 9` 变「已完成」，改为按时长增量判定 |
| 广告页回不到主界面 | `am start -n <宿主 MainActivity>` 万能穿透（`punch_home()`） |
| 返回键按多了触发「确定要退出吗」 | `dismiss_popups()` 里已处理 |
| Git Bash 把 `/sdcard/xxx` 转成 Windows 路径 | 命令前加 `MSYS_NO_PATHCONV=1` |
| adb 写中文路径失败 | 用 `adb exec-out screencap -p > 文件`，重定向交给 bash |
| 中文输出乱码 | 设 `PYTHONIOENCODING=utf-8` |
| 启动文件夹 `.cmd` 里路径被写成正斜杠 | `start` 不认，自启静默失败。已弃用 `.cmd` 方案 |

## 七、风险

自动化可能违反服务条款，存在被风控的可能。用自己账号，后果自负。

本方案做的是「在安卓环境里正常观看广告」，不是伪造广告回调——后者属于欺诈广告主，
不在本项目范围内。
